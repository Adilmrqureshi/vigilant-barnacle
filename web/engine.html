The Engine Behind the Games

Every game on this site is only a few hundred lines of Rust. Not because they're simple — because of the engine underneath them.

Why build an engine?

The hard part of making a game isn't the game — it's everything around it: how entities are represented, how behaviour is organised, how state is shared, how any of it gets tested. I spent the hours (many, many hours) thinking that through once, in a small ECS-style engine, so that every game after it became cheap to build.

Snake, Pong, Breakout and Space Invaders were each built in a sitting — complete with rendering, UI, restart flow and a test suite — because the engine already answers the structural questions. Below are the ideas it's built on.

1. Entities are just data

There is no class hierarchy. An entity is a rectangle plus a set of optional components — have them or don't. A paddle is an entity with a render colour. A ball is the same thing plus physics. Composition over inheritance, assembled with a builder: 

let ball = Entity::new(rect)
    .with_tag(Tag::Ball)
    .with_render(WHITE)
    .with_physics(Physics::new());

2. Tags and queries

Games never walk raw entity lists. They ask the world for what they care about, and get an iterator back. One line of engine code replaces a filter loop in every system of every game: 

for enemy in world.with_tag_mut(Tag::Enemy) {
    enemy.transform.x -= speed * input.dt;
}

3. Systems are plain functions

All behaviour lives in free functions with one shape: fn(&mut World, &mut GameState, &Input). No traits, no scheduling framework, no magic. A game is a list of these functions, run in order every frame: 

let game = Game::new(world)
    .with_update_systems(vec![
        direction_system,
        movement_system,
        food_system,
        collision_system,
    ])
    .with_render_systems(vec![render_board, ui_system]);

That list is the whole architecture of a game. Reading it top to bottom tells you exactly what happens each frame, in what order.

4. Resources: shared state without globals

Not everything is an entity. Pong's two scores, Snake's direction and step timer, the Invaders fleet's marching direction — that's game-wide state. The engine stores it in a type-indexed map (TypeId → Box<dyn Any>), so any system can look state up by its type, safely: 

world.insert_resource(Scores { player: 0, cpu: 0 });

if let Some(scores) = world.get_resource_mut::<Scores>() {
    scores.player += 1;
}

5. Input is data, so everything is testable

Systems never touch the keyboard. The main loop samples input once per frame into a plain struct (including the frame's delta time), and systems consume that. The payoff: every mechanic runs headless. A test builds a world, fakes an input, calls the system directly — no window, no GPU: 

#[test]
fn cannot_reverse_into_itself() {
    let mut world = snake_world();
    let input = Input { left: true, ..Default::default() };

    direction_system(&mut world, &mut state, &input);

    assert_eq!(snake.next_dir, Dir::Right); // ignored!
}

Every game ships with a test suite like this, and they all run in CI on every pull request.

6. Lifecycle: the dead-flag pattern

Removing entities mid-frame invalidates every index into the world, so nothing is ever removed mid-frame. Systems just mark entities dead; one engine call sweeps them up afterwards. Breakout's bricks and Invaders' bullets both live and die through this: 

brick.alive = false;   // any system, any time
world.despawn_dead();  // one safe sweep

7. Events: detection tells, consumers decide

Some systems detect things; several others need to react. In Space Invaders one bullet-hit means a score bump, a fleet speed-up, and two despawns — and one day a sound effect. Instead of one function doing all of it, the detector emits a typed event and any number of later systems read it. Events live exactly one frame; the explicit system order above decides who sees them: 

// detection
world.emit(BulletHit { bullet, invader });

// any number of consumers, later in the list
for hit in world.events::<BulletHit>() {
    // score it, despawn it, play a sound...
}

The result

The engine is ~400 lines. It doesn't try to be Bevy or Unity — it makes exactly one promise: a new game costs an afternoon, not a rewrite. Each of the games on the homepage is a single file you can read top to bottom, and each one exercised the engine enough to grow it a little: Snake added directional input, Breakout added the dead-flag sweep, Pong added a second score. Hours into the engine so that minutes go into the games.
